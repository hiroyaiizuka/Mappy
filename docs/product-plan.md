## 1. 目指す体験

Obsidian のノートを、文章を書く画面と構造を考える画面の両方から扱えるようにする。XMind に近い素早いノード操作、Light Mindmap に近い手軽な移動・拡大縮小、MarkMind のようなリンク・画像の扱いやすさを、通常の Markdown ファイル上で実現する。

- 同じノートを Markdown／マインドマップで切り替えられる。
- 左にマップ、右に Obsidian 標準の Markdown エディタを並べ、編集結果を随時反映できる。
- ノードに内部リンク、外部リンク、画像を表示し、その場で利用できる。
- キーボードで兄弟・子ノードを追加し、編集・移動・折りたたみを行える。
- 拡大縮小中や本文更新後も、見ていた位置と選択をできるだけ維持する。
- 添付画像のように横軸へ章を並べ、下位項目を上下へ交互に伸ばすタイムラインを利用する。
- ドラッグだけでノードの並べ替えと親変更ができ、移動先が事前に分かる（XMind に近い操作感）。
- 空白をダブルクリックして 2 つ目以降のマインドマップ（フリートピック）を作り、あとで本体の枝にできる（XMind のフリートピックに相当）。
- 通常マップ・タイムラインに加えて、階層図（ルートを上に置く段揃えの木）の表示を選び、イシューツリーやロジックツリーを描ける。

今回の優先事項は、機能数よりも Markdown を壊さないことと操作の応答性である。関連線、境界線、PDF 注釈、付箋メモ、共同編集は含めない。フリートピック（M7）、階層図（M8）、AI 機能（M9、有料オプション）は後続段階として本書に置き、M1〜M4 の受入条件を優先する。

## 3. 保存と表示の基本方針

### Markdown を正本にする

保存する内容は Vault 内の通常の `.md` と添付ファイルである。マップ用 JSON を別の正本として持たない。表示設定には必要に応じて frontmatter を使い、選択や一時的なズーム位置などの表示状態は内容と分ける。

現在の保存仕様は以下とする。

- H2 をルート、その下を順序なしリストのインデントで表す。文書直下の見出しが H2 だけ、または見出しがない場合はこの形式を使う。
- H2 以外の見出しがある既存文書は従来の見出し階層を維持する。本文の箇条書きを自動的にノードへ変えない。
- 箇条書きの最初の行、または見出しの文そのものをノードに表示し、別のタイトル欄を要求しない。空のノードを追加し、その場でテキストを入力する。
- 本文は原文範囲を保持する。リストの直接本文は最初の子より前の継続行を扱い、子リスト後の親の文章は保存したまま子の移動範囲へ含めない。
- ノードの移動では、そのノードに属する本文と子孫も一緒に扱う。
- 複数の最上位区画がある文書は、最初の見出し区画を本体、それより後ろの最上位区画をフリートピックとして自由配置する（§5 M7）。見出しのない文書、および最初の H2 より前に文書直下の箇条書きがある文書は、ファイル名を使った表示専用の仮想ルートを本体にする。どちらの場合も表示のためだけに見出しを書き足さない。
- コードブロック内の `#` は見出しとして扱わない。
- 見出しのない文章も保持し、勝手に削除・見出し化しない。
- 閲覧やレイアウト変更だけで、本文全体を整形し直さない。

リストの深さには6階層の制限を設けず、CommonMark の構文に従ってインデントを解釈する。従来の見出しモードだけは H6 が上限で、それを超える子追加・移動を拒否する。番号付き・タスクリストと配下の枝はノード化せず原文を保持する。

旧見出し形式からの変換は右クリック「リスト形式に変更」またはコマンド「現在のマップをリスト形式に変更」で実行し、マップの Undo で復元できるようにする。閲覧では書き換えない。本文の箇条書きが新しいノードになるなど、タイトル・件数・親子関係が変わる変換は拒否する。

### 文章とマップの同期

Markdown 側の見出し・箇条書きの追加・削除・階層変更・順序変更・本文変更をマップへ反映する。箇条書きの階層はインデント変更で更新できる。マップからの操作は、対象範囲への変更として Markdown に反映する。

同期の成立条件は「片側の変更が表示される」だけではない。未保存の編集、同じファイルを開いた複数ビュー、外部変更、Undo／Redo、日本語 IME を含めて内容が失われないことを条件にする。更新が競合した場合は、古い状態による上書きを防ぎ、再読込や操作のやり直しを案内する。

### ノードの内容

- 内部リンクは `[[ノート]]`、別名付きリンク、見出し・ブロックへのリンクを対象にする。
- 外部リンクと通常の Markdown リンクをクリックできるようにする。
- 画像は `![[画像.png]]` と `![説明](画像.png)` を基本にする。
- 画像を追加するときは Obsidian の添付ファイル設定に沿って保存する。
- リンクを開く操作、ノード選択、ドラッグ、テキスト編集を混同しない。
- 本文が長い場合はノード内で全量を広げず、本文表示・編集へ移れるようにする。

API、更新処理、責務の分割は [architecture.md](./architecture.md) で扱う。

## 4. 基本操作の推奨案

| 操作 | 初期割り当て |
| --- | --- |
| ノード選択 | クリック、矢印キー |
| 兄弟追加 | ノード選択中に Enter |
| 子追加 | ノード選択中に Tab |
| テキスト編集 | F2、ダブルクリックでインライン編集 |
| 編集確定／取消 | Enter／Escape。Tab は確定して子を追加 |
| リンク候補 | `[[` / `![[` でノート・パス・別名・添付の候補。候補表示中は Enter／Tab を候補選択に使う |
| 削除 | Delete／Backspace。本文と子孫を含む変更を Undo 可能にする |
| 折りたたみ | Space またはノードの開閉ボタン |
| 並べ替え・親変更・切り離し | ドラッグ。移動先を事前表示する。ノードのない空白で離すと、その枝が新しいフリートピックになる |
| トピックを追加 | 空白のダブルクリック、または空白の右クリック「トピックを追加」。押した位置に空の最上位区画を置き、その場で入力する |
| フリートピックの移動・合流 | トピックのルートをドラッグ。木ごと動き、空白で離すと frontmatter `mappy-topics` だけが変わる。ノードの上で離すとその子の枝になる（移動先を事前表示）。Escape で元の位置に戻す |
| 本体の移動 | 本体のルートをドラッグ。トピックは画面上の位置を保ち、`mappy-topics` の全項目が本体基準で書き換わる |
| 移動 | 背景ドラッグ、トラックパッドのスクロール |
| 拡大縮小 | ピンチ、Ctrl/Cmd＋スクロール、＋／−ボタン |
| 全体表示 | Fit ボタン |
| Markdown／マップ切り替え | ツールバーとコマンドパレット |

キー入力はマップにフォーカスがあるときだけ受け付ける。本文編集や日本語変換中の Enter／Tab を構造操作に使わない。通常のスクロールを拡大縮小へ強制的に置き換えず、カーソル中心のズームと表示領域の移動を別々に検証する。既存の Obsidian ショートカットと共存させる。

上部の子追加・兄弟追加などの操作行は設けず、キーボードと右クリックメニューから操作する。キャンバスを全面に広げ、レイアウト切り替えを左下、Markdown 表示・分割を右上、ズームを右下に浮かせて配置する。通常マップは直角線を使い、ルート周囲を広めに空ける。展開中の折りたたみ操作は枝の分岐点にカーソルを合わせると丸い − を表示する。補完はノード用 textarea の独自 UI であり、標準 Markdown エディタの補完をそのまま埋め込んだものではない。

## 5. 段階的ロードマップと受入条件

### H0a: 開発基盤

製品機能より先に、静的検査・単体テスト・配布物の確認を繰り返せる土台を作る。H0a の完了は、マップ操作の検証環境まで完成したことを意味しない。

- TypeScript の strict 型チェック、ビルド、ESLint と Obsidian 向けルール、EditorConfig による書式設定を整える。
- Vitest と CI を用意し、後続の Markdown 解析・変更・レイアウトを単体で検証できるようにする。
- manifest などのメタデータと配布物を検査する validator を用意する。
- 専用 test-vault の生成と、配置前の preflight を用意する。
- 10／100／500／2,000 ノードの fixture と、必要な受入条件・実機確認の計画を用意する。
- 公開前チェック、保存・同期の設計、まだ判断していない項目を文書化する。

**受入条件:** 一つの品質確認コマンドで静的検査・既存テスト・ビルド・配布物検査を実行でき、CI でも同じ判定になる。fixture と確認計画が共有され、失敗時にどの条件が壊れたか分かる。マップ UI やブラウザ操作テストの完成は、この段階の合格条件に含めない。公式 lint を通すだけでコミュニティ審査通過を保証する、という扱いにはしない。

### H0b: M1 とともに追加する DOM／ブラウザのハーネス

検証は3層に分ける。① Vitest（Node 環境、`obsidian` はモック）による純粋ロジックと DOM のテスト、② Obsidian に依存しないブラウザ検証ページ、③ 専用 Vault を開いた Obsidian 実機での確認（`docs/harness.md` の E01〜E29。CDP で `artifacts/e2e-*.js` を実行する）。③が E2E に相当し、②は E2E の代替ではない。

②の目的は、①で測れない実測サイズ・フォント・画像遅延・ポインター操作・ズームの見た目と、③では回しにくい性能計測を、Obsidian を起動せずに繰り返すことにある。

- 製品と同じ core / layout / interaction を読み込み、fixture を切り替えられるページを作る。Obsidian の API はモックし、保存・リンク解決・テーマ・IME はこのページで検証しない。
- 選択、パン、ズーム、開閉、ペインのサイズ変更などをブラウザで再現する。
- 日本語・同名見出し・リンク・画像・コードブロック・不均等な枝のケースを拡充する。
- 10／100／500／2,000 ノードの fixture で描画時間と入力反映時間を記録し、§6 の仮目標を実測値で置き換える。基準端末・ブラウザ・条件を `artifacts/` に残す。
- ブラウザで代用できない Obsidian の Editor／Vault／リンク解決や IME の動作は、③の手順で確認する。

**受入条件:** ②で M1 の主要操作を再現でき、表示崩れと応答性を確認できる。①②③それぞれの範囲が明確で、②の成功を③の成功と呼ばない。10／100／500／2,000 ノードの描画・入力反映時間が条件付きで記録されている。現在は①②③が揃い、②は fixture 切替と選択・パン・ズーム・開閉・ペインのサイズ変更を headless Chrome で再現して `artifacts/browser-harness/` に記録している。描画時間は時刻の生値までで、基準端末・条件・p95 を伴う性能計測は未完成のため、H0b 全体の完了は宣言しない。

### M1: 閲覧 MVP

- H2＋箇条書き、または既存の見出しと本文からツリーを作り、右向きのマップを表示する。
- 閲覧用の Markdown／マップ切り替えと、標準エディタとの左右分割を用意する。編集操作をまたぐ履歴の保証は M2 で検証する。
- Markdown の編集をマップへ反映する。
- 内部・外部リンク、移動、拡大縮小、Fit、折りたたみを実装する。

**受入条件:** 閲覧だけでは元ファイルを変更しない。見出しの変更がマップへ反映され、コード内の見出しや本文が誤ってノードにならない。リンクを開ける。編集後も不要な Fit を行わず、選択と表示位置を保持する。明色・暗色テーマ、ペインの大きさ変更、ビューを閉じて再度開く操作で破綻しない。

### M2: 双方向編集

- ノードのタイトル編集、兄弟・子追加、削除、並べ替え、親変更を実装する。
- ドラッグだけで兄弟間の並べ替えと親変更を行い、挿入位置を事前表示する（XMind 相当）。ドラッグ中はノードの半透明のゴーストがポインターに追従し、元の位置のノードは薄く残る。移動先にはドラッグ中ノードと同じ大きさの薄い青の枠を仮ノードとして置いて既存の兄弟がその分だけ避け、移動先の親からその枠へ太めの丸い青線を引く。ノード矩形の上下（タイムラインの第一階層は左右）各 30% を兄弟の前／後、中央を子の末尾とする。自分自身・子孫・仮想ルート直下のリスト項目・H6 超過は受け付けない。ドロップは最後に表示した位置を実行し、Escape で取り消せる。画像ファイルのドロップは従来どおり添付になる。
- Markdown 側の編集は `editor-change` を受けて 45 ms の debounce 後にマップへ反映する。未保存の入力、分割表示、別ウィンドウ、同一ファイルの別 leaf、IME 変換中、10〜2,000 ノードで遅延（配置まで最大 136 ms）や欠落がないことを実機で確認した（2026-09-18）。連打中は debounce の性質上、打鍵が止まってから反映する。
- Markdown の対象範囲へ変更を書き戻し、本文・リンク・画像構文・子孫を保持する。
- Undo／Redo、複数ビュー、外部変更、日本語 IME の取り扱いを固める。
- 対応する Markdown の位置とノードへ相互に移動できるようにする。

**受入条件:** 全操作を元へ戻せる。ドラッグでの並べ替え・親変更が Markdown の順序・階層と一致し、ドロップ前に挿入位置が見える。Markdown の入力が保存を待たずにマップへ反映される。Markdown／マップを切り替えても未保存の内容を保持し、Undo／Redo が意図した操作に適用される。ノード変更の前後で無関係な本文や frontmatter が変わらない。同名のノードを取り違えない。外部更新と編集中の変更が衝突しても古い文書で上書きしない。日本語変換の確定でノードが追加されない。従来の形式で H6 を超える見出しを生成せず、リスト形式では深い階層の追加・移動を扱える。

### M3: 画像と操作性の充実

- ローカル画像、画像の貼り付け・追加、サイズ指定を扱う。
- 本文を読み書きする導線と、ノート・画像・PDF 等の内部リンク候補の選択を整える。
- バランス配置などを追加し、キーボードとドラッグの動作を磨く。
- H2＋リスト形式で6段階を超えるツリーを扱う。旧形式の変換は明示操作で行い、原文範囲と構造を検証する。
- タッチ操作、小さい画面、フォーカス表示、読み上げ可能な操作名を確認する。

**受入条件:** 日本語や空白を含む画像パスを扱える。画像が欠けていてもノード全体が壊れない。遅い画像読込でノードが重ならず、表示位置も大きく飛ばない。貼り付けを繰り返して既存の添付を上書きしない。リストの子を移動しても、本文の箇条書きと混同しない。

### M4: 横軸タイムライン

添付画像を基準に、ルートを左端へ置き、第一階層を横軸上に順番に配置する。下位の枝は上・下へ交互に配置し、本文・リンク・画像も通常マップと同じデータで表示する。日付や期間の入力は必須にしない。

- 横軸の項目順は Markdown の順序と一致させる。
- 枝の大きさを考慮して間隔を取り、隣接する枝の重なりを防ぐ。
- マップ／タイムラインの切り替えで内容を書き換えない。
- 通常マップと同じ選択、編集、開閉、ズームを利用する。
- ルートは濃い面、第一階層は枠付き、下位項目はテキストだけとする。線はテキストの手前で止め、閉じた枝には非表示の子孫数を表示する。

**受入条件:** 添付画像のような長い講座構成を、横軸と上下交互の枝で表現できる。長文・画像・深い枝が混在してもノードが重ならない。並べ替えが Markdown と両方に反映される。折りたたみと再展開の前後で内容が欠落しない。日付比例の目盛りやガントチャートは、この段階の要件に含めない。

### M6: 表裏切替と Excalidraw 連携

- 「マップと Markdown を切り替え」を 1 コマンドで往復させ、ユーザーがホットキーを割り当てられるようにする。既定ホットキーは登録しない。
- frontmatter に YAML 真偽値 `mappy: true` を持つノートだけをマップとして開く。`mappy-layout: timeline` は任意の初期表示設定とし、省略時は通常マップにする。レイアウトボタンの明示操作でこの設定を更新し、次回も選んだ表示へ戻す。Excalidraw の対話フレームなど他プラグインが内部で開く leaf でも同じ識別規則を使う。
- Option/Alt を押したドロップで Excalidraw のネイティブ要素として挿入する。Excalidraw 既定の挿入ダイアログは維持し、Mappy ノートから新しく作られた embeddable／Markdown image の外枠だけを透明にする。コマンドからは現在のレイアウトと折りたたみを反映する。
- 挿入後の図面は元ノートと同期しない。ルート要素の `link` で元ノートへ戻れる。

**受入条件:** 新規マップには `mappy: true` と H2 ルートが入る。通常ノートは明示的にマインドマップ化するまでマップ表示・トグル・Excalidraw 挿入の対象にならない。解除では Mappy のプロパティだけを消して本文と他の frontmatter を保つ。トグルで未保存内容を失わず、同じ leaf で往復できる。トグルで Markdown にした leaf は開き直しても Markdown のまま。Excalidraw が無効でも Mappy は通常どおり動き、Excalidraw を後から有効化・再読込してもドロップが効く。挿入した要素は 1 グループで、ルート・第一階層・下位の見た目と線の接続が map view と対応する。Mappy を無効化するとフックと `setViewState` の差し替えが外れる。

### M7: フリートピック

ノードの木とは別に、マップ上の任意の位置へ XMind のフリートピックに相当する最上位トピックを置く。Markdown 側では 2 つ目以降の最上位区画（リスト形式では H2 とその配下のリスト、従来の見出し形式では最上位見出しの区画）そのものであり、新しい記法を持たない。位置だけを表示状態として frontmatter `mappy-topics` に持ち、内容と表示状態を分ける（§3）。付箋メモは採用しない（§7）。

- 表示: 文書の最初の見出し区画を本体のルートにし、それより後ろの最上位区画をフリートピックとして配置する。位置は `mappy-topics` に見出しの文をキーとしてレイアウト別に持ち、未設定なら本体の近くに重ならない既定位置へ置く。既存の「ファイル名の仮想ルートで束ねる」表示は、見出しのない文書だけに残す。
- 追加: 空白のダブルクリック、または右クリック「トピックを追加」で文書末尾に新しい最上位区画（リスト形式では `## `）を追加し、その場でインライン入力する。押した位置を保存する。
- 編集: 通常のノードと同じ操作（インライン編集、子追加、本文、リンク・画像、折りたたみ）。マップ側の改名は `mappy-topics` のキーも同じ差分で更新する。Markdown 側の改名で位置が失われた場合は既定位置に戻る。
- 移動: ドラッグで位置を変える（frontmatter だけが変わる）。ノードの上へドロップするとその子になり（区画→リストの枝への変換）、本体の枝を空白へドロップすると新しいフリートピックになる（枝→区画への変換）。変換は本文・画像・インデントを保ち、タイトル・件数・親子関係が変わる変換は拒否する。
- 削除・Undo: 区画ごと削除し、マップの履歴で戻せる。
- 通常マップ・タイムライン・階層図で同じトピックを表示し、位置はレイアウトごとに保持する。Excalidraw 挿入（M6）に含めるかは M7 の中で決める。

**受入条件:** フリートピックの追加・編集・移動・合流・切り離し・削除を元へ戻せる。トピックを扱っても本体のノード・本文・他の frontmatter が変わらない。Markdown 側で 2 つ目の最上位区画を書くとマップにフリートピックとして現れ、マップ側の編集が Markdown に反映される。フリートピックを持つ文書を Mappy 以外で開くと、通常の見出しと箇条書きとして読める。複数の H2 を持つ既存文書は内容を変えずに本体＋フリートピックの表示へ移る。

### M8: 階層図表示

通常マップとタイムラインに続く第三のレイアウト「階層図」。ルートを上に置き、同じ階層を同じ段に揃えて下へ広げる（イシューツリー・ロジックツリー・組織図・WBS を描くための形）。名前は用途ではなく形で付ける。データと操作は通常マップと共通で、`mappy-layout: hierarchy` を任意の初期表示設定にする。

- 階層ごとに段を揃え、兄弟の順序は Markdown の順序と一致させる。
- 枝の幅を考慮して間隔を取り、長い日本語や多数の兄弟で重ならない。
- 選択、編集、並べ替え、折りたたみ、ズームを通常マップと同じにする。
- レイアウトボタンと frontmatter の扱いは M6 のタイムラインと同じ規則にする。Excalidraw 挿入は現在のレイアウトを反映する。

**受入条件:** 切り替えで内容を書き換えない。折りたたみと再展開の前後で内容が欠落しない。並べ替えが Markdown と両方に反映される。2,000 ノードで操作可能である。

### M9: AI 機能（有料オプション）

有料オプションとして AI 機能を提供する。無料の状態では AI 機能が完全に無効で、他の機能に影響しない。用途の候補はノードへの質問、ノードをタスクとして子ノードへブレイクダウン、ノードから画像を生成して添付。課金方式は未定（参考: TaskChute for Obsidian の AI 機能は買い切りで計画）。詳細は M9 に着手する時点で詰める。

- 着手前に決めること: 課金・ライセンス確認の方式、ネットワーク利用の開示（README・審査）、外部へ送るデータの範囲とオプトイン、API キー等の設定の保存先とモバイル互換。
- 最初の用途を1つに絞り、生成結果は通常のノード編集と同じ経路で Markdown に書く。

**受入条件（この段階）:** 上記の決定事項が本書に書かれ、無料状態で AI 関連のコードがネットワークへ接続しないことをテストで示せる。機能そのものの受入条件は決定後に書く。

### M5: 配布・審査準備

- 公式の開発・審査要件に照らして、manifest、互換性、ライフサイクル、依存関係、設定 UI、文言、配布ファイルを確認する。
- デスクトップとモバイルで、宣言した対応範囲を実機検証する。
- README に保存形式、基本操作、制限、復旧方法、ネットワーク利用の有無を記載する。
- リリース手順とバージョン整合を確認し、公開用ライセンスを確定する。

**受入条件:** 宣言した対応環境で主要操作が通る。無効化・再有効化・ペインの閉開後にイベントや表示が残らない。必要な配布物だけでインストールできる。自動検査と実機確認の結果が記録され、既知の制限が README に反映される。

公式の出発点: [プラグイン作成ガイド（公式原文）](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Plugins/Getting%20started/Build%20a%20plugin.md)、[公式サンプルプラグイン](https://github.com/obsidianmd/obsidian-sample-plugin)、[公式 ESLint プラグイン](https://github.com/obsidianmd/eslint-plugin)。

## 6. 応答性の仮目標

以下は**未測定の仮目標**であり、達成済みの数値ではない。最初の実装を計測し、基準端末・Obsidian バージョン・テーマ・画像条件を記録したうえで調整する。

| 対象 | 仮目標 | 計測条件 |
| --- | --- | --- |
| 500 ノードのテキスト編集 | 入力から画面反映まで p95 100ms 以下 | debounce、解析、配置、描画を含める。画像転送時間は分ける |
| パン・ズーム | 基準端末で 60fps を目標 | 操作中に文書全体の再解析・再配置を走らせない。フレーム時間を記録する |
| 2,000 ノード | 操作可能で内容を失わない | 初回表示、展開・折りたたみ、編集、長い枝を計測し、必要なら画面外の描画を省く |
| 起動時の負荷 | マップを開くまで重い処理を遅延する | 通常ノートの編集時に全 Vault を再走査しない |
| 配布サイズ | H0a で基準値を保存し、増分を追跡する | 一律の上限を未検証で置かず、依存追加の効果と負荷を比較する |

10／100／500／2,000 ノードを共通 fixture とする。ノード数だけでなく、深い一列の枝、多数の兄弟、長い日本語、リンク・画像の密度も変える。自動計測で確認できる範囲と、トラックパッド・IME・モバイルでの実機確認を分けて記録する。

## 7. 主要な判断と残る課題

| 項目 | 現時点の判断 | 再検討する条件 |
| --- | --- | --- |
| 保存形式 | 最新選択は H2＋箇条書き。Markdown 正本で本文・リンク・画像を保持する | 従来の見出し文書を勝手に書き換えず、安全な明示変換を提供する |
| 深い階層 | リスト形式は6階層制限なし。従来の見出し形式は H6 まで | 実機の深い枝・大規模文書での操作性を測定する |
| 本文表示 | 必要なときに読んだり編集したりできる形 | ノード内の全文表示が重要な用途だと分かった場合 |
| 描画方式 | HTML ノード＋SVG の線を第一候補にする | 計測で応答性を満たせず、差分更新や画面外の省略でも改善しない場合 |
| 外部製品コード | まず自前実装し、機能と操作を参考にする | MIT 等のコードを取り込む具体的な必要が生じ、表示義務とライセンスを確認した場合 |
| 公開用ライセンス | 未選択。ローカルでは権利を留保する扱い | 公開前にユーザーが選択する。Light の MIT を Mappy に自動適用しない |
| マップ識別子 | YAML 真偽値 `mappy: true` を必須識別子にする。`mappy-layout` は任意の初期レイアウトに分離し、レイアウト選択時に書く | ファイル種別を扱う Obsidian の公開 API が提供された場合 |
| ビューの切替方法 | Excalidraw・Kanban と同じ `setViewState` の差し替え。依存なしの `patchMethod` で解除と素通しを保証 | Obsidian が公開 API でファイル種別ごとの既定ビューを提供した場合 |
| Excalidraw 連携 | 公開 API `ExcalidrawAutomate` のみ。Option ドロップとコマンドでネイティブ要素、対話フレームでライブ表示 | Excalidraw がフックを複数登録できる API に変えた場合、または双方向同期の要望が明確になった場合 |
| フリートピック | M7 で扱う。文章は 2 つ目以降の最上位区画そのもので新記法を持たない。位置は frontmatter `mappy-topics` に見出しの文をキーとしてレイアウト別に持ち、Mappy は flow 形式で書き、Obsidian の Properties が書き直す block 形式も読む。マップ側の改名はキーも更新し、Markdown 側の改名で位置が失われたら既定位置に戻る | 同名のフリートピックを区別する需要、または見出しの文を識別子に使えない事情が出た場合 |
| 付箋メモ | 採用しない。用途はフリートピック（M7）で吸収し、図としての注釈は Excalidraw 連携で扱う。LEV-27 で試作した本文末尾の `mappy-memo` コードフェンスは Markdown 正本にとって異物（閲覧でリンクが効かず、Mappy 専用の記法）になるため merge せず、frontmatter の位置保存（YAML サブセットの読み取りとキー単位の差し替え）だけを M7 へ転用する | 構造にしたくない注釈（レビューコメントなど）の需要が明確になった場合 |
| 階層図（イシューツリー） | M8 で扱う。ルートを上に置く段揃えの木で、イシューツリー・ロジックツリー・組織図を描く。レイアウト名は用途ではなく形（「階層図」、id は `hierarchy`）で付ける。データ・操作は通常マップと共通 | 左→右の段揃えの需要が明確になった場合はレイアウトの向きを選択式にする（XMind の「ロジック図（右向き）」に相当） |
| AI 機能 | M9 で有料オプションとして扱う。着手前に課金方式・開示・送信範囲・オプトインを決める。無料状態ではネットワークへ接続しない | 課金方式や審査要件の変更、または無料機能として提供する判断があった場合 |

H0a で検査とデータ保全の検証基盤を整え、H0b と M1 で画面を動かして確認し、M2 で編集時のデータ保全を満たす。そのうえで、毎日の操作に必要な機能から順に追加する。

まだ採否を決めていないアイデアは本書に書かず、Linear の「Ideas」親 issue の下に溜める。採用を決めたときに本書へフェーズと受入条件を書く（[linear-workflow.md](./linear-workflow.md)）。
